# Анализ текущей ситуации с ИС компании "Александрит"

## I. Существующие проблемные места

### Системные проблемы
- **Циклическая зависимость**: CRM → API MES → очередь → MES
- **Дублирование данных** между Shop DB и MES DB
- **Отсутствие синхронизации статусов** между системами
- **Длительная обработка входных 3D-файлов** (до 30 минут) блокирует ресурсы
- **Нет асинхронной обработки** входных 3D-файлов

### Проблемы с RabbitMQ
- **Длинные задачи** (2-30 минут) блокируют обработку очереди
- **Все три системы** (CRM, MES API, Shop API) используют одну очередь

### Проблемы с MES
- **Медленная загрузка интерфейса** (жалобы операторов)
- **Большой объем данных** (рост +100 заказов/месяц) без оптимизации

## II. Потенциальные проблемные места

### Риски масштабирования
- Линейный рост нагрузки без горизонтального масштабирования
- Все компоненты связаны жестко, сложно масштабировать отдельные части
- Хранилище S3 может стать узким местом

### Риски отказоустойчивости
- **RabbitMQ**: единственный экземпляр становится единой точкой отказа

### Риски производительности
- **MES**: фильтрация по времени создания требует индексов - рост времени задержки линейный

## III. Рекомендации для устранения нежелательных ситуаций

### Архитектурные улучшения
1. **Убрать циклическую зависимость**:
   - CRM должна создавать задачи напрямую в очередь
   - API MES использовать только для внешних интеграций

2. **Единый источник истины**: выбрать одну БД для хранения заказов (предпочтительно Shop DB)

3. **Синхронизация данных в реальном времени** через события

4. **API Gateway**: для управления внешними вызовами API MES

### Оптимизация обработки 3D-файлов
1. **Асинхронная обработка**:
   - Немедленный ответ "заказ принят"
   - WebSocket или polling для уведомления о готовности

2. **Распределенная обработка**:
   - Вынести обработку 3D в отдельный микросервис
   - Горизонтальное масштабирование воркеров

3. **Предварительная валидация**: проверять файлы до постановки в очередь

### Оптимизация RabbitMQ
1. **Разделение очередей**: создать отдельные очереди для разных типов задач:
   - Быстрые задачи (обновления статусов)
   - Длительные задачи (обработка 3D-файлов)
   - Системные задачи (синхронизация данных)

2. **Кластеризация RabbitMQ**: настроить кластер для отказоустойчивости

3. **Dead Letter Queues**: для обработки неудачных задач

4. **Приоритетность сообщений**: сначала обрабатывать новые заказы

### Оптимизация MES базы данных
1. **Индексация**: создать составные индексы для частых запросов (дата создания + статус)

2. **Партиционирование**: разделить таблицы заказов по месяцам/кварталам

3. **Кэширование**: внедрить Redis для кэширования:
   - Списков заказов
   - Статистических данных
   - Часто запрашиваемых заказов

4. **Read Replicas**: для разделения нагрузки чтения/записи

### Мониторинг и управление нагрузкой
1. **Внедрить мониторинг**:
   - Длины очередей RabbitMQ
   - Времени обработки задач
   - Загрузки БД
   - Доступности сервисов

2. **Настроить автоматическое масштабирование** по нагрузке

3. **Ограничить внешние вызовы** API MES (Rate Limiting)

### Стратегия масштабирования
1. **Горизонтальное масштабирование**:
   - Разделить монолит MES API на микросервисы
   - Балансировщик нагрузки для веб-приложений

2. **База данных**: рассмотреть переход на более масштабируемое решение или шардинг

### Улучшение клиентского опыта
1. **Система уведомлений**: автоматические уведомления о статусах заказов

2. **Прозрачные сроки**: реалистичные оценки времени обработки

3. **Личный кабинет**: возможность отслеживания заказа в реальном времени

## IV. Ближайшие перспективы

- Мониторинг и алертинг
- Индексация БД MES

### Средний приоритет (1 месяц)

- Асинхронная обработка 3D-файлов
- Оптимизация фронтенда MES

### Долгосрочные (2-3 месяца)
- Рефакторинг архитектуры
- Горизонтальное масштабирование
