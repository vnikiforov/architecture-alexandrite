
# Анализ решения по логированию для ИС компании "Александрит"

## Ключевые пользовательские и бизнес-процессы, требующие логирования:

1. Оформление заказа клиентом: Загрузка 3D-модели, расчет цены, создание заказа в CRM.

2. Управление заказом продавцом: Подтверждение, согласование.

3. Производственный цикл в MES: Назначение заказа оператору, изменение статусов (в работе, выполнено, проблемы).

4. Межсервисное взаимодействие: Обмен сообщениями через RabbitMQ о новых заказах и изменении статусов.

5. Интеграция с внешними системами (API User).

## Логи необходимо собирать со всех компоннтов, исполняющих код и обрабатывающих бизнес-логику

* Frontend-приложения (для критических ошибок, аналитики действий): Internet Shop, MES, CRM.
* Backend-сервисы (основные источники): Shop API, CRM API, MES API.
* Базы данных (логи медленных запросов, ошибок): Shop DB, MES DB.
* Очередь сообщений: Messages Queue (RabbitMQ) – логи доставки, ошибок обработки.
* Файловое хранилище: 3D-files storage – логи операций загрузки/скачивания.
* Инфраструктура: контейнеры, виртуальные машины, сетевые компоненты.

## Список необходимых логов с уровнями

**Уровень INFO (нормальная работа бизнес-процессов):**

1. Заказ создан: [time], customer_id, order_id, total_amount, source(shop/crm/api)

2. 3D-файл загружен: [time], customer_id, order_id, file_id, file_size, checksum

3. Статус заказа изменен: [time], order_id, old_status, new_status, changed_by (system/user_id)

4. Заказ назначен на оператора: [time], order_id, operator_id, assigned_by

5. Сообщение отправлено в очередь: [time], message_id, routing_key, source_service, payload_summary (order_id, status)

6. Сообщение получено из очереди: [time], message_id, consumer_service, processing_status (started/success)

7. Пользовательская сессия: [time], user_id, action (login/logout), session_duration

8. Расчет цены выполнен: [time], order_id, calculation_input_hash, calculated_price

**Другие уровни логирования:**

* DEBUG: Детализация алгоритмов (например, шаги расчета цены), полные тела запросов/ответов между сервисами. Включается точечно для отладки.

* WARN: Предупреждения о нестандартных, но обрабатываемых ситуациях: повторная отправка сообщения, таймаут при обращении к S3, fallback на кэш.

* ERROR: Ошибки, нарушающие конкретную операцию, но не работу сервиса: ошибка валидации файла, недостаток средств, неудачная попытка записи в БД (с последующим успешным retry).

* FATAL / CRITICAL: Критические ошибки, останавливающие работу сервиса или его ключевой функции: потеря соединения с БД, недоступность очереди сообщений, ошибка инициализации приложения.

## Мотивация

### Цели логирование

1. Оперативное устранение сбоев - быстрое определение сервиса-виновника и причины инцидента, сокращение времени восстановления (MTTR).

2. Аудит и безопасность - отслеживание действий пользователей (кто, что и когда сделал), особенно для финансовых операций и доступа к персональным данным.

3. Понимание поведения пользователей - анализ воронки продаж, выявление точек отказа в интерфейсе (например, на этапе загрузки 3D-модели).

4. Обоснование принятия архитектурных решений - данные о нагрузке, частоте вызовов API и времени ответа помогают планировать масштабирование.

### Технические и бизнес-метрики, на которые повлияет логирование

1. SLA/SLO по доступности заказа: Логи ошибок на каждом этапе (от оплаты до производства) позволят измерить и улучшить процент успешных заказов.

2. Среднее время выполнения заказа (Lead Time): Цепочка логов о смене статусов даст точную картину о задержках (ожидание дизайна, производство, логистика).

3. Конверсия на этапах воронки: Логи событий в интернет-магазине (просмотр -> добавление в корзину -> расчет цены -> оплата).

4. Производительность операторов (MES): По логам о назначении и завершении задач можно оценивать нагрузку и эффективность.

5. Стабильность интеграций: Частота и характер ошибок при обмене данными между Shop API, CRM API и MES через RabbitMQ.

### Приоритизация внедрения (логирование + трейсинг)

1. Первая очередь (критично для бизнеса):

    * MES API + MES DB + MES (Frontend): Ядро производства. Сбои ведут к прямым финансовым потерям и остановке цеха. Трейсинг цепочки "назначение -> изготовление" обязателен.

    * Shop API + Shop DB: Точка входа денег. Логирование финансовых транзакций и заказов критично.

    * Messages Queue (RabbitMQ): Центральная артерия системы. Мониторинг очередей, dead letter messages.

2. Вторая очередь (важно для сервиса):

    * CRM API + CRM: Для анализа работы менеджеров и коммуникации с клиентами.

    * Internet Shop: Для анализа поведения клиентов и UX.

3. Третья очередь:

    * 3D-files storage, внешние интеграции (API User).

### Архитектура сбора и анализа логов

1. Агент сбора логов: В каждый контейнер/на каждую VM устанавливается агент (например, Fluent Bit). Он читает логи приложений (файлы, stdout) и журналы инфраструктуры, обогащает их метаданными (service_name, pod_name, environment) и отправляет дальше.

2. Централизованное хранилище: Elasticsearch как высокопроизводительное поисковое и аналитическое хранилище. Данные организуются в индексы по типу (logs-app-*, logs-infra-*) и времени (ежедневные индексы).

3. Интерфейс для работы: Kibana для визуализации, поиска и создания дашбордов.

4. (Опционально) Буфер/Очередь: Для устойчивости к пикам нагрузки и сбоям Elasticsearch можно добавить Kafka или Redis между агентом и хранилищем.

### Безопасность и политика доступа

1. Чувствительные данные: Пароли, токены, номера карт НЕ ДОЛЖНЫ логироваться. Использовать маскирование в агентах (Fluent Bit фильтры) или на уровне приложения (logback/log4j patterns). Персональные данные клиентов (ФИО, email) логировать только при необходимости для аудита, рассматривать возможность их псевдонимизации.

2. Доступ к логам: Реализовать через RBAC в Kibana.

    * Уровень 1 (DevOps/SRE): Полный доступ ко всем логам и настройкам.

    * Уровень 2 (Разработчики): Доступ только к логам своих сервисов.

    * Уровень 3 (Аналитики/Менеджеры): Доступ к предопределенным бизнес-дашбордам в Kibana (конверсия, статусы заказов) без доступа к сырым логам.

3. Политика хранения:

    * "Горячие" данные (7 дней): Хранятся на быстрых дисках в Elasticsearch для оперативной отладки. Отдельный индекс на систему/сервис (jewelry-shop-api-logs-2024-05-20).

    * "Теплые" данные (30 дней): Перемещаются на более медленные диски. Необходимы для анализа месячной статистики и расследования нечастых инцидентов.

    * "Холодные" данные (1 год): Архивируются в объектное хранилище (S3) для соблюдения регуляторных требований по аудиту.

    * Размер: Ориентировочно 10-50 ГБ в день в зависимости от объема трафика и детальности логов. Необходим мониторинг роста индексов.

### Анализ логов и алертинг

Алертинг на основе логов:

1. По частоте ошибок: > 5% ERROR-level сообщений от общего числа логов сервиса за 5 минут -> Предупреждение в Slack/Telegram/PagerDuty.

2. По критическим событиям: Появление любого FATAL-лога -> Немедленный инцидент.

3. По бизнес-событиям: Отсутствие новых заказов в течение 30 минут в рабочее время -> Предупреждение для аналитиков.

4. Аномалии (как в примере): Резкий рост запросов "Создание заказа" в 100+ раз относительно скользящего среднего -> Предупреждение о возможной DDoS-атаке или сбое в интеграции.

5. Мониторинг цепочки статусов: Заказ находился в статусе "В работе" > 48 часов -> Алерт для менеджера в CRM.

**Система анализа логов должна уметь:**

* Строить тренды и выявлять аномалии: С помощью Machine Learning features в Elastic Stack (Machine Learning jobs) или сторонних решений (например, в связке с Prometheus и Grafana для метрик).

* Коррелировать события: Связывать логи ошибок в API с логами очереди и базы данных в рамках одного пользовательского запроса (здесь помогает трейсинг, который уже частично отражен на схеме с Jaeger).

* Автоматически создавать инциденты: Интеграция алертов из Kibana с системами типа Jira Service Desk, Opsgenie.
