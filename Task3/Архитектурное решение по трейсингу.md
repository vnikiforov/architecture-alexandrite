
# План внедрения трассировки выполнения запросов в ИС "Александрит"

## Мотивация

1. Потерянные транзакции: 40% проблем с заказами невозможно воспроизвести без трейсинга

2. Сложность диагностики: циклические зависимости между системами затрудняют отладку

3. Длительные операции: обработка 3D-файлов до 30 минут требует мониторинга прогресса

4. Множественные точки отказа: система имеет 8+ точек потенциального сбоя

5. Рост нагрузки: +100 заказов/месяц увеличивает вероятность конфликтных ситуаций при одновременном доступе к общим ресурсам

### Технические метрики, которые улучшатся

1. Время диагностики проблем: сокращение с часов до минут

2. MTTR (Mean Time To Resolution): снижение на 60-70%

3. Процент успешных транзакций: увеличение с 95% до 99%

4. Производительность разработки: ускорение отладки на 40%

### Бизнес-метрики, которые улучшатся:

1. Процент отмененных заказов: снижение на 25-30%

2. Удовлетворенность клиентов (CSAT): рост на 15-20%

3. Конверсия заказов: увеличение на 5-10%

4. Операционные расходы: снижение на 15-20% за счет меньшего времени простоя

## Компромиссы

### Случаи, когда трейсинг не принесет пользы

1. Слишком высокое семплирование (>30%):

    * Перегрузка системы трейсинга

    * Затраты на хранение превысят выгоду

2. Старые системы без поддержки технологии OpenTelemetry:

    * Проприетарные системы (часть MES)

    * Системы на устаревших версиях фреймворков

3. Высокочастотные операции без бизнес-ценности:

    * Технические проверки работоспособности сервисов - регулярные автоматические запросы от систем мониторинга к Shop API, CRM API и MES API для подтверждения их доступности

    * Автоматический сбор технических метрик - периодическое извлечение системных показателей (использование CPU, памяти, диска) мониторинговыми системами

4. Стоимость внедрения превышает выгоды:

    * Малые системы с простым workflow

    * Системы с низкой нагрузкой (<100 транзакций/день)

5. Технические ограничения:

    * Системы без возможности модификации кода

    * Жесткие требования к производительности (latency < 1ms)

### Ограничения текущей архитектуры

1. RabbitMQ: сложность трейсинга между разными очередями

2. 3D файлы: длительные операции (>30 мин) требуют special handling

3. Дублирование данных: трейсы могут показывать противоречивую информацию из разных БД
